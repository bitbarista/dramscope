DRAMSCOPE 1.4  --  C64 memory diagnostic          updated 2026-09-26
====================================================================

Free and open source (MIT). If it finds a fault for you, or saves you from
replacing a chip that was never the problem, you can support it here:

  https://ko-fi.com/bitbarista

DRAMSCOPE.CRT is the test. G1PROBE.CRT is a one-question hardware probe
that has already been answered on both your devices; it is kept only as a
record and does not need running again.


RUNNING IT
----------

It is an EasyFlash cartridge. Load it on an Ultimate II+, a Kung Fu Flash, or
any other cartridge that can be an EasyFlash.

WHAT IT RUNS ON
---------------

  Ultimate II+          confirmed on hardware
  Kung Fu Flash         confirmed on hardware
  EasyFlash 1 or 3      expected -- and flashing one gives you a DEDICATED
                        TEST CARTRIDGE. Untested by us; please report.
  Other EasyFlash carts expected, if the $DE02 emulation is faithful
  A plain EPROM cart    ⚠ NOT FULLY -- see below

⚠ IT IS AN EASYFLASH CARTRIDGE, NOT A PLAIN ROM IMAGE, AND THAT IS NOT A
PACKAGING CHOICE. It boots in Ultimax mode, which is the only mode where the
CARTRIDGE supplies the reset vector instead of the KERNAL -- that is what lets
it start on a machine with no working KERNAL and no working RAM. But Ultimax
only maps $0000-$0FFF of RAM. Writing $02 to the EasyFlash register at $DE02
releases GAME, leaving Ultimax for 8K mode with the cartridge still at $8000,
and the other 60 KB becomes reachable.

A plain EPROM cart has no $DE02 -- GAME and EXROM are strapped in hardware and
cannot change. Strapped for Ultimax it boots and runs, but the $DE02 write does
nothing, the border goes ORANGE to say so, and it can only ever see 4 KB.
Strapped for 8K or 16K the KERNAL supplies the reset vector, so it can only be
entered through the autostart handshake -- which needs a working KERNAL, stack
and zero page, discarding the whole point.

⚠ GOT A CARTRIDGE NOT LISTED? Run G1PROBE.CRT. It sweeps all eight values of
$DE02 and reports which, if any, leaves Ultimax with the cartridge still
mapped. GREEN means DRAMscope will work on that device.

It boots in Ultimax and takes its reset vector straight from the cartridge,
so it needs NO WORKING KERNAL and NO WORKING RAM to start -- not even the
stack page. A machine too broken to reach BASIC can still be tested, which is
the machine most worth testing.

Tested with every DRAM out of its sockets (2026-09-27): it starts and reports
that low memory does not respond. ⚠ AND IT NOW TELLS YOU WHICH KIND:

  RED, STEADY        low memory will not hold a value, but something else in
                     $0000-$0FFF does. So RAM IS FITTED and a chip is faulty.
  RED, FLASHING      nothing anywhere in $0000-$0FFF holds a value. NO RAM
  slowly on and off  FITTED, or the PLA is not selecting it. There is no chip
                     to find -- check the sockets are populated first.

Before this, both cases showed the same steady red, which sent people hunting
for a faulty chip on a machine that had none in it.

⚠ BUT THE CARTRIDGE HAS TO BE MAPPED WITHOUT A MENU.

  Kung Fu Flash   remembers the last cartridge and boots straight into it,
                  so the no-RAM case works.
  Ultimate II+    its menu is itself a C64 program -- it runs on the 6510 and
                  draws using C64 RAM. With no DRAM fitted the menu cannot
                  run, so you never get as far as choosing the file. Start it
                  once with RAM in place, or use a KFF for that job.

⚠ AND IT CANNOT TEST MEMORY THAT IS NOT THERE. The screen itself lives in
DRAM, so on a machine with nothing fitted the border is the only output there
can be. A solid colour IS the report in that case. You get "low memory does
not respond"; you do not get a map, a bit number or a chip name, because
none of those can be worked out without memory to test.

IT DOES NOT STOP. One run takes about 80 seconds, including a 12-second
wait in RETENTION; then it counts the run and starts over, and keeps going
until you reset the machine. Leave it running. The bottom line of the screen
says so too: RUNS UNTIL YOU RESET.

Everything accumulates. A cell that has failed stays red even if later
runs are clean. BAD BYTES only ever grows. And once anything has failed the
border pulses RED instead of grey for the rest of the run, so you can walk
past an hour later and know.

That is what leaving it running is for: a chip that fails once an hour
looks perfect on a single run, and it is the one worth finding.


IS IT STILL ALIVE?
------------------

A spinner turns beside the name of the test that is running, and the border
pulses a couple of times a second, all the way through.

  ** A BORDER THAT HAS STOPPED PULSING MEANS IT HAS HUNG. **

The pulse is deliberately slow -- almost exactly one cycle per second, set
by a hardware timer rather than by how fast the test is running, so it
cannot speed up during a faster phase. That is about a third of the rate
considered a photosensitivity risk (three flashes per second). The spinner
moves faster but is a single character.

That is the report, not an ambiguity. Tell me which test it was on and the
colour it froze on.


BORDER COLOURS
--------------

Before the test proper, the border reports faults the display cannot:

  white    the cartridge has control
  red      FATAL: the scratch bytes $F5-$FE will not hold a value, but
           something else in $0000-$0FFF does -- RAM is fitted, a chip is bad
  red, flashing slowly on and off
           FATAL: nothing in $0000-$0FFF holds a value at all. No RAM fitted,
           or the PLA is not selecting it. ⚠ CHECK THE SOCKETS ARE POPULATED
           before suspecting a chip -- there may be no chip to suspect
  purple   FATAL: the screen page is unusable
  orange   FATAL: this device ignores $DE02 and cannot leave Ultimax
  blue     FATAL: $C000-$CFFF is unusable
  black    the cartridge never got control at all

During the test the colour says which test is running, and pulses:

  yellow DATA LINES       cyan   ADDR LINES      green  MARCH B
  cyan   MARCH LR         purple ROW/COLUMN      orange LOW MEMORY
  grey   OWN MEMORY       blue   RETENTION

COLOUR RAM has no colour of its own: it is checked inside OWN MEMORY, so the
border is grey for it.

At the end: GREEN clean, LIGHT RED fault found.


THE MAP
-------

The 16x16 grid IS the address space, one cell per 256-byte page. Row is the
high digit of the address, column the next one -- so top left is $0000 and
bottom right is $FF00. The digits are printed along the top and down the
left, so a cell's address can be read straight off the grid.

The SHAPE of a fault usually says more than its address: a stripe, a
quadrant, a scatter each mean something different.

Under the grid is its key:

  64K MAP: #=FULL *=LIGHTER X=BAD

X is the one to look for. FULL and LIGHTER are explained below.

THE CHECKLIST
-------------

The right-hand panel is headed TESTS AND RESULTS. It lists every test in
the order it finishes, with its result, so you can see at a glance what has
been done to the machine:

  DATA LINES   OK        ..   not started yet
  ADDR LINES   OK        /    running -- the marker turns
  MARCH B      OK        OK   passed
  MARCH LR     OK        X    FAILED, and STAYS failed
  ROW/COLUMN   OK
  LOW MEMORY   OK      RETENTION's marker counts its 12-second wait down
  OWN MEMORY   OK      in seconds, so that row stays alive too.
  COLOUR RAM   OK
  RETENTION    OK

Under DATA LINES and ADDR LINES are their individual lines, bit by bit, so
a single bad line is named rather than inferred.

Each new run puts the passed tests back to '..' and fills the column in
again, so you can always see how far through the CURRENT run it is.

⚠ A test that has failed ONCE keeps its X for the rest of the run, even if
every later run is clean. It is the one thing that does not reset. That is
the whole point of leaving it going: the fault that happens once an hour is
the one worth finding, and a display that forgot it would be worse than none.

RUNS and BAD BYTES are on the title line: completed runs, and bytes failed
so far. Both count the whole session, and both are ORDINARY DECIMAL NUMBERS.

⚠ A $ ON THIS SCREEN ALWAYS MEANS AN ADDRESS. The counters used to be printed
in hex with a $ in front; they are counts, not addresses, and nobody has run
the test $0012 times. Now the only $ you will see is the one in front of a
memory address like $4037, which matches the hex digits along the top and down
the side of the map.

⚠ COLOUR RAM is a SEPARATE 1K x 4 chip and not part of the 64 KB. When it
fails you get wrong colours rather than a crash, so it gets blamed on the
VIC. It is never counted against the DRAMs and never names a 4164.

The marks say how HARD each region was tested, in reads and writes per
byte -- not whether it was reached. Everything except two bytes is reached.

  #       FULL: 45 reads and writes of every byte -- March B, March LR,
          six row/column patterns and the retention wait
  *       LIGHTER: about 9 per byte, a shorter march. These are the regions
          the test itself has to stand on: zero page, the stack, its
          workspace, the screen, and its own 4 KB. Every byte is still
          tested -- just not hammered as hard
  X       a BAD BYTE somewhere in that page
  -       yellow, and moving: this is the page being tested right now
  .       dark, nearly invisible: not reached yet. On a finished run there
          are none -- every page of the 64 KB is tested, including
          $D000-$DFFF, which is marched with the I/O chips banked out

Everything else is covered, and the verdict line says so in numbers
rather than in words:

  59,648 FULL + 5,886 LIGHTER = 65,534.

That is ALL the RAM. A C64 has 65,536 ADDRESSES, but two of them are not
memory: $0000 and $0001 are the CPU's data-direction register and banking
latch. So 65,534 is the whole of it, not a shortfall.


IF IT FINDS A FAULT
-------------------

It prints the failing DATA BIT, and under it the chip that carries that bit:

   MEMORY FAULT, FIRST BAD BYTE AT $4037
   BITS                               D0
   LIKELY                             U21
   8X4164 ASSUMED. 41464? D0-D3=1 CHIP.

The address is where the FIRST bad byte was found, so there is something
concrete to probe. The map shows every page that has one.

⚠ THE ROW SAYS "LIKELY" AND MEANS IT. The bit number is measured; the chip
name is a lookup. That row assumes a board with eight 4164s -- read the part
number off one of your own RAM chips and check.

*** BEFORE YOU DESOLDER ANYTHING ***

THE BIT NUMBER IS MEASURED. THE CHIP NAME IS A SUGGESTION.

DRAMscope proves that data bit D0 (or whichever) did not hold what was
written to it. That is a measurement and it is reliable. Turning that bit
into a chip is a LOOKUP, and a lookup rests on two things the tool cannot
check for you:

  1. THAT YOU HAVE THE BOARD IT ASSUMES. It cannot see which board it is
     plugged into. Check the assembly number yourself.

  2. THAT THE FAULT IS IN THE CHIP AT ALL. A failing bit means the fault is
     somewhere ON THAT DATA LINE. The RAM chip is the likeliest part on it,
     but these look IDENTICAL to any software test:

       - a dry or cracked solder joint on that pin
       - a corroded, bent or spread socket contact
       - a broken track between the RAM and the CPU
       - the PLA, or whatever gates /CAS to the RAM
       - the CPU or VIC end of the same line

So work in this order, cheapest and most reversible first:

  1. Reseat the chip. Socketed RAM that has sat for forty years is a common
     fault all by itself.
  2. Inspect and reflow the joints on that chip and its socket.
  3. Check continuity along the data line, RAM pin to CPU pin.
  4. Only then swap the chip -- and keep the old one until the repair is
     confirmed, because it may well be good.

If you replace a chip and the same bit still fails, the chip was not the
fault. That is information, not a wasted part: it points at the line.

⚠ DRAMscope is offered with no warranty of any kind (see LICENSE). It tells
you what it measured. Deciding what to replace is yours.


If your board has only TWO RAM chips they are 41464s, each FOUR BITS WIDE, so
four of the bit numbers share a single chip. The last line tells you which
group failed. It does not name the chip, because the two 41464 boards do not
agree with each other and nothing on screen can tell them apart -- use the
chart below.


THE CHART -- WHICH CHIP CARRIES WHICH BIT
-----------------------------------------

⚠ THIS TABLE IS ALSO A SEPARATE ONE-PAGE FILE, CHIP-CHART.TXT, MEANT TO BE
PRINTED AND KEPT BY THE BENCH. It carries the same table plus worked examples.

Find your assembly number: it is printed on the board itself, usually near
the front edge, as "ASSY 250469" or similar.

  ASSY      RAM         D0    D1    D2    D3    D4    D5    D6    D7
  ------------------------------------------------------------------
  326298    8 x 4164    U21   U9    U22   U10   U23   U11   U24   U12
  250407    8 x 4164    U21   U9    U22   U10   U23   U11   U24   U12
  250425    8 x 4164    U21   U9    U22   U10   U23   U11   U24   U12
  250466    2 x 41464   <-------- U10 -------->  <-------- U9 ------->
  250469    2 x 41464   <-------- U10 -------->  <-------- U11 ------>

⚠ THE TWO 41464 BOARDS ARE THE OPPOSITE WAY ROUND FROM EACH OTHER. On the
250469 the lower number carries the lower bits; on the 250466 it is reversed.
Do not guess from one to the other -- check the assembly number.

⚠ 250466 IS A LONG BOARD WITH TWO RAM CHIPS. Counting the chips does not tell
you whether you have a long or short board, so an earlier version of this
sheet saying "short board? 2 chips" was wrong.

All three 8 x 4164 boards are identical, so the on-screen names are right for
any of them.

  ** THE BIT NUMBER IS TRUE ON EVERY C64. THE CHIP NAME IS NOT. **

The designators are for Assy 250407. A short board carries two 41464s --
four bits each -- so those names are simply wrong there, which is what the
last line is warning about. The tool cannot tell which board it is in.

If EVERY bit fails it names no chip at all and points at the PLA instead.
Eight dead DRAMs is not the likely reading, and sending you to desolder
eight chips would be worse than sending you nowhere.


WHAT IT CANNOT DO
-----------------

Refresh cannot be switched off from software on a C64 -- the VIC refreshes
regardless, and blanking the screen actually gives the CPU more cycles
while refresh carries on unchanged. So RETENTION tests against a
WORKING refresh. It catches cells leaking faster than refresh can sustain.

Temperature is the other lever and it is not a software one:

  ** RUN IT AGAIN ON A MACHINE THAT HAS BEEN ON FOR AN HOUR. **

ROW/COLUMN uses row and column adjacency as the C64 ADDRESSES them, which
is correct. They do not model the physical layout
inside any particular manufacturer's die, and do not claim to.
